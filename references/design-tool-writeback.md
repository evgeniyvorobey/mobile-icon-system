# Design-Tool Write-Back

Use this reference when icon-system work needs to return to Figma, Pencil, or a filesystem package. It separates real design-tool write-back from safe handoff planning so reviewers can tell what was actually changed, what was only prepared, and what still needs a connected tool.

## Provenance Rule

Never claim that Figma or Pencil was used unless an actual MCP tool call happened in the current work. A scaffolded plan, exported SVG, screenshot review, REST API read, or user-provided file is not the same as a Figma MCP or Pencil MCP write.

Every handoff should state one of these evidence levels:

| Evidence level | Meaning | Allowed claim |
|---|---|---|
| Figma MCP write-back | A connected Figma MCP tool created or updated native Figma content | "Updated Figma via MCP" with file, node, tool, and verification evidence |
| Figma MCP read-only | A connected Figma MCP tool read design context, screenshots, variables, or metadata | "Inspected Figma via MCP" with file, node, and tool evidence |
| Code Connect handoff | Code-to-design mappings were prepared or published through Code Connect | "Prepared or published Code Connect mappings" with mapping evidence |
| Pencil MCP write-back | A connected Pencil MCP tool updated a `.pen` document | "Updated Pencil via MCP" with document, nodes, tool, and verification evidence |
| Filesystem-only | Work was produced from repo files, exported assets, screenshots, or user input | "Prepared filesystem handoff" only |

If the evidence is a plan, say it is a plan. If a tool was unavailable, say which fallback was used.

## Workflow Choice

### Figma MCP write-back when connected

Use Figma MCP write-back only when the host exposes a real Figma MCP server and the user has authorized the target file. Official Figma docs describe the MCP server as giving agents structured design context, including components, variables, layout data, and other design details, and current write capabilities can create or update Figma designs using real Figma primitives and existing design-system libraries.

Write-back flow:

1. Detect the Figma MCP tool surface and confirm the target file URL, page, node, or component set.
2. Read current design context first. Capture variables, component names, variant properties, frames, and screenshots.
3. Prepare `figma-writeback-plan.md` with each intended frame, component, variable, or asset update.
4. Ask for confirmation if the change mutates a shared library or production file.
5. Execute the write with Figma MCP only after the plan is specific enough to review.
6. Verify by reading the updated Figma context, capturing screenshots, or comparing REST API JSON before and after.
7. Record the actual MCP tool names, target file key, node IDs, timestamps, and verification evidence.

Do not represent a filesystem SVG export as native Figma content unless it was actually inserted or linked by a Figma write tool.

### Code Connect handoff

Use Code Connect when the goal is to connect repository components to Figma Dev Mode, not to redraw icons on the canvas. Figma developer docs describe Code Connect as a bridge between a codebase and Figma Dev Mode, connecting repository components directly to design-file components. Published Code Connect entries can show true-to-production snippets from the design system instead of autogenerated examples.

Code Connect handoff should capture:

- Figma component URL or node ID.
- Repository component path and export name.
- Supported platforms or frameworks.
- Variant and prop mapping, including state, size, tone, and selected or disabled behavior.
- Snippet owner and publish status.
- Whether the mapping was only planned, generated locally, or actually published.

Code Connect can improve MCP implementation context, but it is not proof that Figma canvas content was edited.

### Pencil MCP for `.pen`

Follow the repo contract in [`design-tool-integrations.md`](design-tool-integrations.md): `.pen` documents require Pencil MCP for read and write work. Filesystem reads of `.pen` are not a valid inspection path for this skill.

Pencil flow:

1. Confirm Pencil MCP is available before touching a `.pen` workflow.
2. Open or identify the active document through Pencil MCP.
3. Read guidelines and current selection or node state before planning changes.
4. Prepare `pencil-writeback-plan.md` with the intended batch, target nodes, and expected verification.
5. Mutate only through Pencil MCP.
6. Export or screenshot through Pencil MCP for verification.
7. Record the actual Pencil MCP calls and document evidence.

If Pencil MCP is unavailable, produce a filesystem handoff and clearly state that the `.pen` file was not inspected or updated.

### Filesystem-only fallback

Filesystem-only mode is the safe fallback when no design-tool MCP is connected. It can still produce useful deliverables:

- SVG, PDF, PNG, vector drawable, or asset-catalog outputs.
- `asset-manifest.csv` with asset IDs, source paths, formats, states, and target mappings.
- `code-connect-map.md` as a planned mapping worksheet.
- `verification-checklist.md` for designer or engineer review.

Filesystem-only mode must not claim design-tool write-back. It can say "ready for Figma import", "ready for Pencil import", or "ready for Code Connect mapping" when the package is prepared.

## REST API Verification

Use the Figma REST API for read-only inspection or verification when MCP is unavailable or when reviewers need machine-readable evidence. Official Figma docs state that the REST API can inspect a JSON representation of a file, and the file endpoint `GET /v1/files/:key` returns the referenced document as a JSON object. File endpoints can also return JSON or image representations of a whole file or individual nodes.

REST reads can help:

- Inventory pages, nodes, components, styles, and component sets.
- Compare before and after JSON snapshots when a write-back was performed elsewhere.
- Verify node IDs and component metadata used in Code Connect mapping.
- Render or inspect specific nodes with endpoint parameters when authorized.

REST reads do not by themselves prove an MCP write happened. Pair them with an actual MCP execution log if the claim is "written back through Figma MCP".

## Handoff Folder Schema

Use `scripts/scaffold_design_tool_handoff.py` to generate a safe handoff folder. The folder contains:

| File | Purpose |
|---|---|
| `figma-writeback-plan.md` | Target file, planned Figma changes, actual MCP execution log, and Figma verification evidence |
| `pencil-writeback-plan.md` | Target `.pen` document, planned Pencil batch, actual MCP execution log, and Pencil verification evidence |
| `code-connect-map.md` | Component-to-code mapping worksheet for Dev Mode handoff |
| `asset-manifest.csv` | Exported assets and their planned Figma, Pencil, and code targets |
| `verification-checklist.md` | Provenance, visual QA, accessibility, platform export, and sign-off checklist |

The scaffold is intentionally conservative: it creates plans and evidence slots. It does not call Figma MCP, Pencil MCP, Code Connect, or the Figma REST API.
